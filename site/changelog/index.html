    Changelog¶

    All notable changes to the Vault plugin will be documented in this file.

    The format is based on Keep a Changelog, and this project uses date-based versioning (YYYY.MM.PATCH).

    [Unreleased]¶

    Added¶

    • Replication targets now show what the last sync actually did. A target that connected but had nothing new to copy previously just read "Synced", which looked the same as a sync that transferred data — so replication could appear to "connect but not do much". Each target now shows an explicit Up to date state when a sync found nothing new, a per-sync summary (jobs synced, new restore points, bytes transferred, and any failures), and the time replication last fully succeeded. These counters are stored with each run, so they are visible on page load and after a refresh, not only in the moment a sync finishes. Closes #287.
    • Contributor build and run guidance is now discoverable from the repository root and docs site. Added explicit local development prerequisites and workflows across CONTRIBUTING.md, README.md, and docs pages so new contributors can find compile/build/run/lint/test/docker instructions, frontend-dev notes, and architecture links from a single entry path. Closes #341.

    Security¶

    • Updated Go and web dependencies to their latest compatible releases and resolved a high-severity advisory in the web nanoid dependency. gosec, govulncheck, and the Go linter pass clean, and the MCP integration remains on the go-sdk v1.7.0 API.

    Changed¶

    • A scheduled deep verify no longer piles onto a destination that a backup is still writing to. Deep verification streams and re-hashes every stored item, so running it against the same storage destination as an in-progress backup saturated the shared disk and network — the backup slowed to a crawl and looked frozen, with nothing in the logs to explain it. Vault now defers a scheduled deep verify while a backup is running on the same destination and records why in the activity log, letting the deep verify run at its next scheduled tick instead. Quick verification (existence and size checks only) is light enough to keep running alongside a backup, and an on-demand verify you trigger yourself is never deferred. Closes #290.

    Fixed¶

    • A container's database dump is no longer lost when the restore does not reload it. When a restore left the SQL dump in place — because the restored volume was the newer, consistent copy, the container was not running, or the database never became ready — the dump only ever existed in a temporary staging directory that Vault cleaned up when the restore finished, so there was nothing left for an operator to find. Vault now copies the un-reloaded dump to a durable, discoverable location and reports the exact path in the restore progress and logs: the custom restore destination when one is set (<destination>/<container>-database.sql), otherwise beside the container's first restored volume (for example /mnt/user/appdata/<container>-database.sql). The file name is prefixed with the container name so restores that share a parent directory do not collide, and the container backup guide now documents where the dump lands for in-place and custom restores. Closes #289.
    • The web console no longer gets stuck on an endless "connecting" screen after a plugin upgrade until you clear site data. The page that the Unraid shortcut opens (app.php) served the app shell with no cache headers, so a browser — Brave especially — could keep a copy of it from before an upgrade. That stale shell still pointed at the previous JavaScript bundles, which the upgrade had replaced with new content-hashed filenames, so the browser fetched bundles that no longer existed and the app never finished loading. The shell is now sent with the same "never cache" policy the daemon already applies to its own index.html, so every visit loads the shell that matches the installed version. Closes #288.
    • The Dashboard "Largest backups" tile no longer shrinks after incremental backups run. It was computed from only the last handful of runs, so once a job's large full backup dropped out of that short window the tile fell back to the size of the most recent — much smaller — incremental. It now reads the largest backup per job from the latest 200 history records, so the full backup remains represented well beyond the short recent-runs window. Closes #286.
    • A custom restore location is now honoured when restoring a plugin from a deduplicated destination. The deduplicated plugin restore only looked at the restore directory passed to it directly and ignored the restore_destination setting as a fallback, unlike the container restore path which already checks both. In current use both are set to the same value so there was no visible effect, but the two independent paths could have drifted apart in future. The plugin restore now falls back to the setting when no directory is passed, keeping the two in step. Closes #274.
    • A plugin backed up to a deduplicated destination now keeps its .plg installer file. The deduplicated plugin backup only stored the plugin's config directory, leaving out the .plg installer at /boot/config/plugins/<name>.plg. A restore from such a backup — for example onto a fresh Unraid install — brought the configuration back but not the installer, so Unraid might not recognise the plugin on the next boot. The .plg is now stored alongside the config in the same restore point and written back on restore, matching what the non-deduplicated plugin backup already did. Backups taken before this change simply have no installer to restore, exactly as before. Closes #273.
    • Restoring selected files from a plugin backup on a deduplicated destination no longer restores the whole plugin. When a plugin backup lived on a dedup destination and you picked specific files to restore, the file-picker selection was dropped on the way through the deduplicated restore path and the entire plugin config directory was written back instead. The selection now carries through to the folder restore that reconstructs the files, so only the chosen files are restored — matching how the same picker already worked for non-dedup plugin restores. Closes #271.
    • Backup sizes now read the same everywhere they are shown. Four operator-facing places still formatted sizes with their own math instead of the shared byte contract, so the same backup could read differently depending on where you looked: the Storage page's saved-backups list stopped at TB with no clamp (a petabyte showed as 1024.0 TB), the Recover Vault wizard always printed raw kilobytes (1048576 KB for a gigabyte), the packaged plugin History page always printed megabytes (1073741824.0 MB for a petabyte), and the transfer-speed label capped at GB/s and disagreed with the app near unit boundaries. All four now go through the same formatBytes contract the app and notifications already use, so a size or speed reads identically across the console, the wizard, the plugin pages, and Discord/webhook messages. Closes #270.

    [v2026.08.00] - 2026-08-02¶

    Added¶

    • Database containers can now be backed up as a proper database dump, not just its files. PostgreSQL, MySQL, and MariaDB containers get an optional "Also save a … dump" tick in the job editor. Vault exports the databases with the server running and stores the dump alongside the usual file backup — copying a database's files while it is writing can capture a torn state that will not load, whereas a dump is always consistent and can be reloaded into a different server version. The dump covers the whole server including users and permissions, so a restore does not come back missing the accounts the application signs in with. It uses the credentials already set on the container, so there is nothing to configure and no second copy of a password for you to look after. If the container exposes no usable root password, the dump is scoped to the database named in its environment instead, since an application user cannot read the whole server. A container that is stopped or stuck restarting is reported plainly rather than silently skipped.

    Restoring puts the folders back and leaves the dump alongside them for you to reload by hand or into a different server version. It is deliberately not replayed over the restored folders: the dump is taken while the server is still running, the folders are copied after it stops, so the folders are the newer copy — and a reload would drop anything written while the dump was still being taken. Where the folders were read from a running server, and so may be mid-write, the dump is the trustworthy copy and is reloaded automatically; if that reload fails the restore fails with it, rather than handing back a database that looks restored and is not. Off unless you tick it. Closes #259.

    • Exclude the same paths everywhere, without editing every job. Settings → Backup Exclusions takes a list of paths that every folder and container backup skips. They are added to whatever a job already excludes rather than replacing it, so a job can still exclude more of its own. Useful for the paths that are never worth backing up anywhere — caches, sockets, scratch directories. Closes #257.
    • Containers can declare their own exclusions with a Docker label. Setting vault.exclude=/config/cache,/tmp on a container tells Vault to skip those paths when backing it up. The exclusions travel with the container, so a template or compose file carries its own answer and adding the container to a job needs no further setup. The paths are matched exactly like ones typed into the job wizard, and the job editor shows which mounts a label is skipping. A label can exclude paths but not the whole container — a catch-all pattern is refused, since the label is written by whoever built the image rather than by the person who owns the backup. On by default; it can be turned off in Settings → Backup Exclusions. Closes #258.

    Fixed¶

    • A container backup now fails instead of quietly saving nothing when every one of its folders is excluded. With a broad exclusion rule — from the global list or a container's own label — it was possible for every backup-eligible folder to be skipped, leaving a backup that reported success but held only the container's configuration. It now stops with an error naming where to look, matching how virtual-machine backups already refuse to run when a VM has no disks they can handle. This applies to deduplicated destinations as well as ordinary ones: the check originally guarded only the ordinary path, so a dedup destination could still record a restore point holding no folder data at all — one that retention might later keep in place of a complete one. The check also runs before the container is stopped, so a backup that cannot produce anything no longer costs it any downtime.
    • Large backups to a dedup destination no longer slow to a crawl and appear frozen. Every time a backup finished a 24 MiB pack, Vault listed the entire _vault/index/ directory on the destination to work out the next index-blob number. That directory gains one entry per pack, so the cost grew with every pack written: a 500 GB folder flushes roughly 21,000 packs and so issued 21,000 listings of a directory holding up to 21,000 entries — hundreds of millions of directory entries pulled across the network in a single run. Progress crawled, got steadily worse the longer a backup ran, and on a remote destination (WebDAV/SFTP/S3) eventually degenerated into connection and DNS timeouts that failed the run. Vault now reads that directory once per backup and counts on from there, so index bookkeeping costs the same on the last pack as on the first. Existing destinations are picked up as-is — no re-upload, repair, or reconfiguration is needed. Closes #256.
    • A slow or stalled browser can no longer hold up a running backup. Live progress events were handed to the WebSocket layer with a blocking send, so once the outbound queue filled — a browser tab left open that had stopped reading, or a flaky connection — the backup goroutine itself waited on it. Progress updates are now discarded rather than queued when a connection cannot keep up, since the next update carries the same information. Events the interface cannot recover by waiting — run completion, item failures, queue changes — are still delivered reliably, so a busy backup never leaves a finished job showing as still running.
    • Backup runs no longer log a spurious "malformed settings JSON" warning. A job item saved without any per-item settings stored an empty value rather than an empty set, so every run that checked it reported the item as corrupt in the log. Nothing was actually wrong and backups were unaffected, but the warning pointed at a healthy item. Items now always store a valid value, and existing ones are read correctly without the warning. Genuinely corrupt settings are still reported.
    • A VM that ignores the request to shut down no longer fails the backup. Cold VM backups ask the guest to shut down gracefully and wait for it. If the guest accepted the request but never acted on it — no ACPI handler installed, sitting at a login prompt, or an application blocking shutdown — the wait timed out and the backup gave up with "waiting for domain … to shut off: timed out with state running", even though Vault already had a forced-stop step ready for exactly this situation. It now falls through to that forced stop, so a stubborn guest is powered off and the backup proceeds. A backup you cancel yourself is still never turned into a forced power-off. The same fix applies when a restore has to stop an existing VM before replacing it. Reported in #255.
    • "No space left on device" now explains itself on an Unraid user share. A backup writing to a path under /mnt/user could fail with a bare out-of-space error while the array showed terabytes free, which reads like a permissions fault or a Vault bug. It is neither: a user share spreads its contents across disks, but any single file is written to one of them, so a large VM disk image fails as soon as the disk it landed on is full — no matter what the array total says. The error now names the directory that filled and, for a user share, explains this and points at the settings that govern it (the share's Minimum Free Space and Split Level), or suggests targeting a specific disk or pool such as /mnt/cache instead. Reported in #255.
    • A dedup backup can no longer report success while leaving data that a later repair would discard. After writing a pack of deduplicated data, Vault recorded it in its local database before writing the matching record to the destination. If the second write failed, the backup still completed successfully, but the destination held data with no record of what was in it — so vault dedup repair, the tool for rebuilding the local database from the destination, would quietly drop it and reveal the backup had been unrestorable all along. The destination record is now written first, so a failure fails the backup immediately and visibly instead of surfacing later as missing data.
    • A backup can no longer be built on top of data that space reclamation has already marked for deletion. When reclaiming space, Vault records its intent to remove a pack before deleting it, so an interrupted run can be finished later. If the deletion itself failed — a destination that is reachable but refusing deletes, for instance — the pack's contents stayed listed as available, so the next backup of the same files would reuse them instead of storing its own copy. That backup then depended on data already marked for removal, and repairing the index afterwards would drop it, leaving the backup unrestorable. Contents of a pack marked for deletion are now excluded from reuse the moment that mark is recorded, while the record itself is kept so the next reclamation retries the delete. The affected backup simply stores its own copy instead. Existing destinations pick this up automatically on upgrade.
    • Repairing a dedup index can no longer lose chunks that a surviving pack still holds. vault dedup repair rebuilds the index by replaying the bookkeeping records stored alongside your backups, and it applied deletion records as it went. Because a chunk is recorded once and space reclamation copies chunks into a replacement pack before retiring the old one, replaying the retired pack's record last left the chunk attributed to it — and applying the deletion then removed the chunk outright, even though the replacement pack still held the data. Restores after a repair could then fail with missing chunks. The rebuild now determines which packs were retired before it replays anything, so the result no longer depends on record ordering. This only affected repair and disaster recovery; normal backups and restores were never at risk.
    • The interface now recovers on its own after losing contact with the daemon. A browser that stopped keeping up — a background tab, a flaky link — was disconnected by the daemon, and any update in flight at that moment was lost. Since a job's completion notice is what clears the progress display, losing that one message left a finished backup shown as still running until the page was reloaded. On reconnecting, the console now re-reads the current run state and reconciles what it missed, so the display corrects itself. The daemon also states plainly that it dropped a connection for falling behind, instead of closing it in a way indistinguishable from a network failure.
    • Per-file progress updates are now rate-limited to roughly one per second. Chunked backups and restores sent a WebSocket event for every single file — 46,000 events for a large music library — each one costing CPU on the server and work in the browser, for updates far faster than anyone can read. Backup, restore, and the restore download phase now report at a steady cadence instead. On-screen progress is unchanged in practice, and the internal stall detector still sees every file and every byte, so a genuinely hung backup is still detected just as quickly.
    • Restoring a differential or incremental container from a dedup destination no longer fails with "no such file or directory". Only the full backup would restore; every later point in the chain stopped with an error naming a directory that does not exist. Dedup backups keep their data in the chunk store rather than in a folder per container, but container restores were being sent down the older path that looks for that folder — a shortcut for restoring a single point directly was in place but sat behind a check that only folders ever reached. Container and plugin backups write a complete record of the item on every run, exactly as folders do, so restoring the chosen point on its own reproduces it correctly. Restores from non-dedup destinations are unchanged. Closes #266.
    • Saving a job in Batch container mode no longer fails with "invalid container_mode". Choosing Batch in the job editor and clicking Save returned an error and refused to save; Sequential saved normally. The job wizard, the backup runner and the rest of the codebase all call this mode stop_all, but the API's list of accepted values had been written as all_at_once — a name nothing else used — so the one value the interface could actually send was the one value the API rejected. Batch mode was therefore impossible to select on any job. The list now matches the rest of the stack. Any job still holding the old value — it could only have been written by the MCP interface, an import or a replication sync, none of which check this field — is converted once, on upgrade, so every such job changes together rather than only the ones that happen to get edited. Those jobs had been running sequentially despite the name, and will now genuinely stop all their containers together. Closes #261.
    • A cold VM backup no longer fails outright and leaves the guest powered off when the guest is slow to stop. Vault asked the guest to shut down and then waited for it, but treated "shutting down" — a passing state on the way to being off, while the guest is still running — as though the guest had already stopped. When a poll happened to land in that window, the backup pressed straight on to start its temporary session and libvirt refused with "domain is already running", so the backup failed while the guest carried on shutting down and stayed off. Because it depended on the timing of a single poll it struck only sometimes, which made it look like a random failure rather than a bug. Vault now waits for the guest to be genuinely off. Reported in #265.
    • A cold VM backup can no longer leave the guest powered off and the job stuck on "running" for hours. After a cold backup stopped a VM and copied its disks, the temporary paused session had to be torn down before the guest was started again. If that teardown failed, Vault returned immediately and never issued the start — so the VM stayed down, the run never finished, the job showed "running" indefinitely, and only restarting the daemon cleared it. The guest is now brought back up whether or not the teardown succeeded, and is resumed rather than restarted when the session is still paused, since a paused guest is just as unavailable as a stopped one. Both failures are reported instead of one hiding the other.
    • A backup that stops responding is now reported as stalled instead of sitting silently on "running". Several problems combined to make a wedged run invisible. The stall watchdog stopped running the moment it cancelled a stalled job, so from that point nothing was written to the log at all — the operator saw a job stuck on "running" with a dead log and no way to tell a working backup from a jammed daemon. Underneath, calls to the virtualisation service could wait forever: they have no time limit of their own, so if libvirt accepted a request and never answered, no amount of cancelling could free the backup, and even opening the connection could hang before anything was watching it. A run that stops making progress is now marked as stalled, with the reason, and that is published to the interface — so a stuck run can be told apart from a healthy one rather than both reading as "running". The run keeps its real status until it genuinely finishes, so nothing is reported as failed that has not actually failed. The watchdog also keeps reporting, at widening intervals, for as long as a cancelled run refuses to finish. Connecting to the virtualisation service is now time-limited, and a cancelled run still stuck on it after a grace period has its connection dropped so the stuck call fails and the run can finish. Dropping it can no longer strand a virtual machine: the shutdown-and-restart step disconnects that safety net first and reconnects if it has already fired, so the guest is still brought back up. Reported in #265.
    • Differential container backups no longer stop and restart containers that have nothing to back up. Every running container in the job was stopped and started again on each differential run, even when none of its folders had changed since the last full backup — pure downtime for no data. Vault now checks the folders first and leaves the container running when there is nothing new, applying the same exclusions as the backup itself so an excluded host-wide mount is never scanned. Full backups, containers marked not to be stopped, and containers that are already stopped all behave exactly as before.

    • Restoring a container to a chosen location no longer merges two of its folders into one. Where a restore sends data somewhere other than its original home, each folder lands in a directory named after the last part of its original path. Two folders whose paths differ only higher up — /mnt/user/app/config and /mnt/cache/other/config, say — therefore both claimed the same directory: their contents were interleaved, files with matching names overwrote one another, and the rebuilt container was pointed at that one directory for both. The clash is now detected before anything is written and the restore stops, naming both folders, rather than reporting success over merged data. Restoring to the original locations was never affected.

    • A restore no longer reports success when reloading a database dump failed part-way. The failure was written to the log and the restore finished normally, even though reloading a dump replaces the existing tables as it goes — so a reload that ran out of time, hit an error, or filled the disk left the database holding only part of its data while the restore said it had completed. Such a failure now fails the restore and says the database should not be relied on.

    • The daemon can no longer hang indefinitely while disconnecting from the virtualisation service. Closing a libvirt connection asked politely first and waited without limit for the answer, which never came if libvirtd had accepted the connection and then stopped responding — the exact situation the connection was meant to be able to break. Because the idle-check that runs before an adaptive backup holds the lock that serialises runs, one such hang stopped every later backup from starting. The polite close is now given five seconds before the connection is broken outright.

    • Restoring a container from a dedup destination to a custom location no longer writes volume data to the original paths while pointing the recreated container at the empty custom directory. The chunked restore path discarded the destination parameter and always wrote files back to the original bind sources, then recreated the container with mounts rewritten to the custom destination — so the running container was destroyed and replaced with one pointing at empty directories, while the data sat orphaned at the original paths. Volume data now lands under the custom destination (matching both the classic restore path and the container's rewritten binds), restoring parity between the two code paths. The classic restore path's volume-target computation is also extracted into a shared helper so the two can never drift apart again.

    • The Dashboard no longer contradicts itself on a fresh install. The Protected tile reported "All items covered" in green beside a red 0-of-N bar while every item was still waiting for its first backup — the caption counted only items missing from every job, and an item queued but never yet backed up is in neither group. It now reads how many are pending.     Fixed¶

    • Anomaly baselines no longer report a 100% failure rate for every job (closes #181). The baseline refresher counted a run as failed unless its status was success — a value the runner never writes (successes are completed) — so every job's stored failure rate was a meaningless constant 1.0. Failures are now counted the same way the reliability detector counts them (failed status or failed items), producing real rates.
    • Database snapshots are now written atomically (closes #182). The pool snapshot and USB safety-net copy were written directly over the previous good file, so a crash, power loss, or full disk mid-save corrupted the very copy the daemon needs for disaster recovery. Snapshots are now written to a temp file and renamed into place only after completing successfully — and if the primary snapshot is ever unreadable at startup, the daemon now also tries the rotated snapshot copies (newest first) before falling back to the USB copy or a fresh database.
    • Post-backup health checks show container names again after a container was recreated (closes #178). In stop-all mode, the health check after restarting containers looked names up by the stored container ID — but when a container had been recreated (update, compose recreate) the runner works with the re-resolved ID, so the check reported the raw 64-character ID instead of the name. Names now resolve through the re-resolved IDs too.
    • Filename validation now rejects single backslashes (closes #179). The path-separator guard in restore-name validation checked for a double backslash due to an escaping mistake, letting a single \ through this specific check (harmless on Linux, but the guard didn't do what it said). It now rejects both / and \.
    • Replication sync results are now honest about failures (closes #177). A sync whose jobs all failed to copy still recorded "success" and announced a completed sync — a false safety signal for an off-site-copy feature. Sync status is now success only when every job synced, partial when some failed, and failed when nothing synced, with the failure count shown on the Replication page (which previously showed failed syncs as "Pending").
    • Replicated restore-point metadata can no longer be silently corrupted (closes #176). The replication origin marker was spliced into restore-point metadata by string concatenation, so a source name containing quotes/backslashes — or metadata like { } — produced invalid JSON, silently stripping checksums and dedup manifest references from every replicated restore point. The metadata is now rebuilt through the JSON encoder and is always valid.
    • Restoring over an existing installation no longer fails on pre-existing symlinks (closes #175). Regular files are overwritten during restore, but symlink and hardlink entries were created without replacing what was already on disk — so restoring a container/folder backup onto a live appdata tree aborted with "file exists" at the first pre-existing link (version symlinks, certificate links, node_modules/.bin). Links are now replaced like files; directories are never silently removed.
    • Deduplicated backups no longer fail outright on a single unreadable file (closes #174). Classic backups skip inaccessible files with a log line, but the deduplicated (chunked) path aborted the entire item on the first permission-denied or vanished file — so the same job succeeded on a classic destination and hard-failed on a dedup one. The chunked walk now skips-and-logs identically, reporting the number of skipped paths in the log and progress message.
    • Automatic database backups are now pruned instead of accumulating forever (closes #184). After every successful run Vault copies its own database to the destination's _vault/ directory, but old copies were never removed — one server had accumulated 136 copies (477 MB) in six weeks, and on quota-limited remotes this growth eventually crowds out real backups. Vault now keeps the newest 14 timestamped copies per destination (plus the vault.db.latest recovery pointer, which is always kept) and deletes older ones after each write.
    • Deleting the last dedup job on a destination no longer destroys the daemon's database backups stored there (closes #183). The dedup chunk repository and the automatic vault.db recovery copies share the _vault directory on every destination; the cleanup that removes an orphaned dedup repo deleted the entire directory — including every database backup. Cleanup now removes only the dedup-owned paths (repo.json, packs/, index/) and leaves the database copies untouched.
    • Replication syncs no longer leak storage connections (closes #173). Each replication sync opened the local storage destination but never closed it; for SFTP destinations that leaked up to four SSH connections per scheduled sync (and orphaned NFS mounts), accumulating until daemon restart. The adapter is now released when the sync completes.
    • Daemon shutdown now waits for in-flight restores (closes #172). A planned restart (plugin update, rc.vault restart) drained active backups but was blind to restores: shutdown could kill a restore mid-write, leaving half-restored appdata or VM disks. Restores now participate in the same drain protocol as backups — shutdown waits for them, and a draining daemon refuses to start new ones.
    • Cancelling a VM backup or restore now takes effect immediately (closes #171). VM operations ignored cancellation entirely: pressing Cancel (or the stall watchdog firing) had no effect until the libvirt backup job finished or its 2-hour timeout expired, and the hypervisor kept writing disk data into a staging directory the runner had already torn down. Cancellation is now honoured within seconds across every VM stage — the in-flight libvirt backup job is aborted (DomainAbortJob), multi-GB disk/NVRAM copies stop at the next 1 MiB chunk, and all shutdown/startup/readiness waits exit early — while VM teardown (restarting a cold-backed-up VM, tearing down the paused backup session) still always completes so a cancelled run never leaves a VM in the wrong power state.
    • Backups of imported jobs no longer crash when a container's stored ID is missing (closes #170). Jobs imported from existing backups (native manifests without per-item IDs, or appdata.backup imports) store containers with an empty ID; when such a job ran while a container with that name existed, the ID-change log line sliced the empty ID and panicked, failing the run with an opaque "Internal error (panic)" on every attempt. ID truncation is now bounds-checked everywhere.
    • SMB capacity probes no longer leak a connection on every check (closes #169). The scheduled capacity probe (and the Storage page's refresh button) opened an SMB session for the space query but never logged it off, leaking one authenticated session plus its TCP connection per probe until the NAS started refusing new SMB connections. The probe now releases the session like every other SMB operation.
    • Empty directories left behind by deleted backups are now actually cleaned up (closes #168). Deleting restore points (retention, manual deletion) removed the files but the sweep that prunes the now-empty parent directories never ran: the storage middleware chain didn't pass the directory-removal capability through to the underlying adapter, so the sweep silently did nothing on every destination. Local, SFTP, SMB, and NFS destinations now prune emptied parent directories again; object stores (S3) and WebDAV, which have no safe "remove if empty" primitive, are skipped cleanly.
    • ZFS incremental and differential chains now record and use the correct parent snapshot (closes #180). The snapshot created by each ZFS backup was never persisted into the restore point, so chained runs silently fell back to sending against whatever vault snapshot happened to be newest on the dataset — a "differential" was really an incremental against the previous run, and snapshot cleanup then destroyed the last full's snapshot (the chain anchor). The result: differential restore chains could not be received (zfs recv: most recent snapshot does not match incremental source). Each backup now records its snapshot per item in the restore point (zfs_snapshots), the next chain run resolves its -i parent from there (falling back to a full backup with a clear warning when the parent is missing or was deleted — including for restore points created before this fix), and cleanup preserves the chain-anchor snapshot alongside the newest one.
    • Automatic retries now actually fire for pre-flight failures and stall-cancelled runs (closes #167). When a run was skipped because its destination failed the pre-flight check (DNS blip, unmounted share), or cancelled by the no-progress stall watchdog, Vault scheduled a retry — but the retry watcher only ever dispatched retries for runs whose status was failed, so those scheduled retries sat in the database forever and never ran. The watcher now claims due retries for failed, skipped, and cancelled runs alike, matching the outcomes retries are scheduled for.
    • Truncated archives can no longer be reported as successful backups (closes #166). When finalising a container-volume, folder, or plugin archive, errors from the tar footer flush, the gzip/zstd trailer, and the final write to disk were silently discarded — so a disk that filled up during the last flush, or a file that shrank while being archived, produced a corrupt/truncated archive that the run reported (and even checksum-verified) as success, discovered only at restore time. All three finalisation steps now fail the backup with a clear error (closing tar writer: …, finalising compression: …, closing archive file: …).
    • Deduplication garbage collection can no longer run while a backup is writing to the same destination (closes #165). Starting a GC (Storage → Run GC, or the automatic reclaim after deleting a dedup job) while a dedup backup was in flight could delete the chunk packs that backup had just written — its restore point only becomes visible to GC at the very end of the run — silently corrupting the new backup so it would fail at restore time. GC now waits for the active backup/restore to finish before it scans (and backups queue behind a running GC), refuses to start during daemon shutdown, and shutdown in turn waits for an in-progress GC to complete.
    • S3 backup verification no longer aborts (and deletes the upload) on large archives (closes #164). S3 Read/ReadRange bound the streamed response body to the same 5-minute deadline used for quick metadata calls, so verifying any archive that takes longer than 5 minutes to stream back failed with context deadline exceeded — and the runner then removed the files it had just successfully uploaded, leaving the run failed and the destination empty. Streamed S3 reads now carry no wall-clock deadline (matching SFTP/WebDAV/local): closing the reader releases the connection, waiting for a dead endpoint's response headers is still bounded (5 minutes), and genuinely hung transfers are cancelled by the stall watchdog. Deep verify and restores from S3 destinations benefit the same way.

    Fixed¶

    • VM backups now honour the job's compression setting. When a libvirt push-backup job finished, Vault asked libvirt for the completed-job record to decide success or failure. On hosts where that record is unavailable at poll time (libvirt reports "no completed job" as a normal reply, not an error — e.g. another tool consumed the record or libvirtd reloaded), Vault misread the reply as a failure even though every byte had been copied, so backups that ran to completion (44+ minutes of real work) were reported as failed on every attempt. Disk format was inferred from the file extension, but Unraid names most vdisks vdisk1.img regardless of format. A qcow2-formatted .img (like the Windows VM in the report) was written out as a raw image and restored as raw while the domain XML still said qcow2 — an unbootable restore. Restoring an incremental chain resolves each step's disk files from the vm_meta.json the backup recorded (with the old filename scan as fallback for pre-existing backups), so chains whose full backup is a .img file flatten correctly; a chain whose disks cannot be resolved now fails loudly instead of silently restoring only the newest increment. qemu-img calls also honour restore cancellation, and layer/metadata filenames are validated before use.

    • Large backups no longer fail with dedup: pack size … exceeds safety bound when an item contains a very large number of files (#118). Oversized manifests are now split through the same content-defined chunker used for file data and stored as ordered segments behind a small envelope, so no single chunk approaches the bound regardless of file count. The split is transparent on restore, existing (v1) single-blob manifests still read unchanged, and because near-identical manifests now mostly re-reference existing segments, manifest storage also deduplicates across snapshots. A clearer early error also replaces the opaque packer failure if any oversized chunk is ever stored.

    • Storage layer rebuilt as a composable middleware chain for uniform reliability across all backends. Every storage destination (local, SMB, NFS, SFTP, WebDAV, S3) is now a thin provider wrapped in a chain – throttle → retry → metrics → logging – so cross-cutting behaviour is identical everywhere instead of hand-rolled per provider. A single transient-error retry layer with jittered exponential backoff (5 attempts, 1s→30s, full jitter) now sits in front of all backends; it classifies timeouts, connection resets, broken pipes, unexpected EOF, and transient HTTP statuses (408/429/500/502/503/504) as retryable while failing fast on auth/permission, 4xx, and user cancellation. This replaces the previous WebDAV-only retry loop and gives S3 and SFTP automatic retry they never had. A new retry-aware WriteFrom write path re-opens the staged source per attempt so a partially-failed upload replays cleanly from the start.

    Added¶

    • Stale-item detection and one-click remediation for backup jobs (#119). When a container, VM, folder, plugin, or ZFS dataset referenced by a job no longer exists on the server, the backup run now skips it instead of failing the whole job with confusing "missing item" errors, records it, and raises an Unraid notification. The Jobs page shows an amber "N missing" badge on affected jobs; clicking it opens a Review missing items dialog that lists each gone item with a per-item Remove button and a Remove all button. Vault never removes items automatically – you decide. Removal is re-validated server-side at click time (an item that has reappeared is left alone) and only drops the item from the job: existing backups and restore points are preserved, so you can still restore what was captured before the source disappeared. Detection degrades safely – if Docker or libvirt is temporarily unavailable, items of that type are treated as "unknown" (never flagged as missing) so a transient outage can't mark everything stale. New endpoints: GET /api/v1/jobs/{id}/stale-items, POST /api/v1/jobs/{id}/stale-items/remove, DELETE /api/v1/jobs/{id}/items/{itemId}; new WebSocket event stale_items_detected.
    • Resilient, parallel restores from remote storage. Restore downloads now recover from transient mid-stream connection drops instead of restarting the whole object and failing the restore: a resumable reader reopens the transfer from the last byte received (built on ranged reads, so it works on every backend – local, SMB, NFS, SFTP, WebDAV, S3). Restores also download multiple files concurrently (bounded by the job's parallel-transfers setting), and a single large plain object (e.g. an unencrypted, uncompressed VM qcow2) is fetched via concurrent ranged GETs assembled on disk – turning a long single-stream download into a parallel one. Encrypted (.age) or compressed objects use the sequential resumable path so the decrypt/decompress pipeline stays correct; checksums are verified on both paths (a whole-file re-read for the parallel path, inline for the sequential path). Restores additionally gained the same no-progress stall watchdog the backup path has – a hung restore is now cancelled (and that cancellation reaches the engine restore phase) rather than blocking indefinitely.
    • Per-job parallel uploads. Each job has a Max parallel uploads setting (1–16). A job's staged files now upload through a bounded worker pool of that size, sharing the destination's bandwidth cap. Existing jobs keep serial behaviour (1) on upgrade so nothing changes unexpectedly on fragile links; new jobs default to 3. Set it to 1 for a flaky or rate-limited remote, or higher for a fast link.
    • SFTP connection pooling. The SFTP backend previously dialed a fresh SSH connection for every operation; it now reuses a small pool of healthy connections (and correctly closes both the SSH and SFTP clients on teardown, fixing a per-operation connection leak). This makes parallel SFTP uploads practical.
    • Storage observability. Per-operation metrics (calls, errors, retries, latency) are tracked per destination, and an opt-in Verbose storage logging toggle (Settings → General, off by default) emits a redacted, structured trace line per storage operation for diagnosing slow or flaky remotes.

    • Empty-directory cleanup. Deleting the last backup under a directory on filesystem-style and SFTP backends now sweeps the now-empty parent directories, so destinations don't accumulate empty folders over time.

    • Anomaly detection and insights (Pillar A). A new internal/anomaly engine watches four signals per job/destination – size drift, duration drift, reliability/verify regressions, and destination capacity trajectory – and surfaces anomalies across every Vault surface. Detectors use robust statistics (median + MAD with the Iglewicz–Hoaglin modified z-score) plus pragmatic secondary rules (a 5× median-multiplier growth rule and a 0.5× asymmetric-shrinkage rule for suspiciously small backups). Each job and destination exposes a Strict / Balanced / Permissive sensitivity knob (Settings → General sets the global default; per-job overrides on the job edit form). Detection runs asynchronously off the backup runner via a bounded, non-blocking evaluator goroutine – a completed run enqueues an evaluation, and a 5-minute trend ticker drives the capacity detector. Anomalies surface live on a new dashboard card, as inline severity badges on job and run-history rows, on a new /anomalies page (filters, keyset pagination, bulk-acknowledge), via Unraid + Discord notifications (severity-gated; default: critical only, with notified_at de-duplication and per-job anomaly:* notify_on overrides), and as three MCP tools (list_anomalies, get_anomaly, acknowledge_anomaly) for AI assistants. Lifecycle is hybrid: soft (info/warning) anomalies auto-resolve on a clean run, criticals persist until acknowledged, and a Mark as expected action raises the baseline floor so deliberate growth stops re-alerting. New endpoints under /api/v1/anomalies, /api/v1/jobs/{id}/baseline, and /api/v1/destinations/{id}/capacity-trajectory; new WebSocket events anomaly.raised, anomaly.updated, anomaly.bulk_resolved, anomaly.bulk_acked, and baseline.updated. Detection is opt-out (anomaly_detection_enabled, defaults to true) and learns a per-job baseline over the first 10 runs (the UI shows a "Learning baseline (N/10)" label until then). Storage adapters gained a Usage() method (free/total bytes) – implemented for local, SFTP, SMB, NFS, and quota-capable WebDAV; S3 reports unsupported. Terminal anomalies older than 90 days are pruned automatically.

    Security¶

    • SFTP private-key file path is now validated before it is read (CodeQL go/path-injection). The admin-configured key-file path is rejected if it contains any .. traversal component (checked both before and after normalisation) and resolved to a clean absolute path before os.ReadFile, mirroring the existing snapshot-path sanitiser.     Fixed¶

    • Vault configuration no longer disappears after an Unraid upgrade or restart (closes #108). Four root-cause-driven changes restore the persistence invariant end-to-end:

    • Non-hybrid USB-backup restoration fallback. The previous startup path only ran the snapshot fallback chain when hybrid mode engaged. The first time the daemon ran in hybrid mode, the on-USB vault.db was renamed to vault.db.backup (the safety net). On any later boot where the pool drive failed to mount in time – exactly what happens after an Unraid upgrade restart, because Unraid launches plugin services before the array finishes mounting – hybridMode stayed false, db.Open("/boot/.../vault.db") saw a missing file and silently created a brand-new empty SQLite schema, and every saved job, destination, and setting became invisible. internal/cli/daemon.go now performs an explicit non-hybrid restoration step: if the primary DB is missing/empty but a USB safety-net backup exists, vault.db.backup is copied back into place (fsynced) before the first db.Open. Operators get a clear log line (Configuration restored from USB backup at …) and, if neither file exists, an explicit warning that the daemon is starting fresh.

    • Pool-mount retry loop on startup. internal/cli/daemon.go now polls unraid.PreferredPool() + unraid.IsMountedPool() up to 15 times with a 2 s interval (30 s window total) before declaring no pool. This catches the common case where the array comes up within a few seconds after the daemon launches and lets hybrid mode engage cleanly, instead of falling through to USB-direct mode for the entire daemon lifetime.
    • Pre-drain USB flush on SIGTERM. internal/api/server.go StartWithContext now invokes a registered preShutdownHook immediately on ctx.Done(), before the runner drain. The daemon registers snapshotMgr.FlushToUSB() as that hook (internal/cli/daemon.go). Previously the final snapshot + USB flush only happened after the (up to 30 s) runner drain returned and srv.ListenAndServe produced ErrServerClosed; if rc.vault escalated to SIGKILL mid-drain (which it did, given a 15 s wait), all in-RAM configuration was lost. A new log line server shutdown: pre-drain flush completed in <duration> confirms the path ran.
    • rc.vault shutdown window extended from 15 s to 45 s with intermediate SIGINT. The plugin's service script (plugin/rc.vault) and the Ansible deploy role's inline rc.vault template (ansible/roles/deploy/tasks/main.yml) now both: poll kill -0 $pid for up to 45 s after SIGTERM (matching the 30 s drain + flush headroom), send SIGINT before escalating to SIGKILL, and log forced-shutdown reasons. The previous one-line stop() (kill $pid; rm -f $PIDFILE; echo "stopped") returned in milliseconds without waiting, which is what introduced the SQLITE_BUSY race observed during make deploy (the new daemon started before the old one finished its flush).

    Verified end-to-end on Unraid against the live "Test Containers", "Folders Backup", and other configured jobs: every rc.vault restart cycle now logs server shutdown: pre-drain flush completed in 1.2-3.0 s → Vault daemon stopped gracefully → fresh startup with Database restoration: source=primary path=/mnt/cache/.vault/vault.db (restored from configured snapshot path). Configuration survives across multiple back-to-back restarts with zero database is locked errors.

New ZIP entries: verify_runs.json (last 25 quick + deep runs), dedup_stats.json (per dedup destination), runtime.json (goroutines, heap, GC, uptime), pools.json (every discovered Unraid pool with its mount status), connectivity.json (Docker socket + libvirt URI probes; errors are captured so "Docker not reachable" is itself the diagnostic), scheduler.json (next-run timestamp per enabled job).
    • Diagnostics ZIP layout is split into per-section files instead of one fat diagnostics.json. Support engineers can now unzip -p bundle.zip jobs.json | jq without paging through unrelated sections. The top-level diagnostics.json is a one-screen overview that omits activity, runs, and the log tail.

    Changed¶

    • SaveSnapshot now runs PRAGMA wal_checkpoint(TRUNCATE) before invoking the SQLite Online Backup API so the resulting snapshot file is self-contained and the WAL is reclaimed on disk. Checkpoint failures are logged but never block the snapshot. New PRAGMA journal_size_limit = 67108864 (64 MiB) at every Open() bounds the WAL between checkpoints.
    • restoreWithFallback runs PRAGMA integrity_check on every successfully-restored tier and falls through to the next tier (primary → default cache → USB backup → fresh DB) when the check fails. A corrupt snapshot can no longer silently become the working database – at worst the daemon starts with a fresh DB and tells the operator to reconfigure.
    • HTTP API shutdown now drains the runner for up to 30 s before the existing 5 s HTTP Shutdown window. A planned restart (plugin upgrade) lets the active per-file upload reach the next boundary instead of being killed mid-stream. After the drain ceiling fires, the existing context-cancel path still tears down mid-flight work. New Runner.Drain(ctx) is the API surface.
    • job_runs.status can now be skipped. Two paths produce skipped runs: a pre-flight check failing to reach the destination, and a scheduled run firing against an open breaker. The History page renders skipped rows neutrally (not red), and the deferred retry watcher picks up preflight-skipped rows for re-attempt.
    • Bandwidth limit no longer offered for local storage destinations. Throttling local I/O slowed backups for no operational benefit. The Storage form hides the field for local destinations and the factory ignores any stale value left in an older config. SFTP, SMB, NFS, WebDAV, and S3 continue to honour the limit.
    • Restore wizard, History timeline, Logs, and Dashboard Recent Activity now show absolute timestamps as the primary label, with the relative form (48m ago) preserved as a hover tooltip. Matches how Veeam, restic, and Time Machine present restore points (closes #81).

    Fixed¶

    • Editing any field on a storage destination no longer silently corrupts the saved password. The Settings → Edit Storage modal pre-fills its password input with whatever the API returned ("••••••••" for any destination with credentials – the redaction marker). Saving the form without retyping the password posted that marker back to PUT /api/v1/storage/{id}, which the server then stored verbatim as the new password, causing every subsequent backup/test to 401. PUT /storage/{id} now runs the incoming config through preserveRedactedSecrets: any sensitiveConfigKey whose value equals the "••••••••" marker is rewritten to the corresponding value from the previously-stored config before persistence. New typed credentials still overwrite as before. The fix is server-side because the trap affected the UI modal AND any other client (MCP tools, ansible automation, direct API scripts) round-tripping a partial edit.
    • S3 destinations no longer fail with Head "//<bucket>./<endpoint>": unsupported protocol scheme "" when the operator pasted a bare-hostname endpoint (e.g. s3.us-east-005.backblazeb2.com, exactly as Backblaze B2's web console displays it). The adapter handed the unmodified string to the AWS SDK, where url.Parse left Host empty and the virtual-host-style bucket-prefix resolver emitted a malformed URL with no scheme. NewS3Adapter now runs every endpoint through normalizeS3Endpoint: bare hostnames are promoted to https://…, schemes other than http(s) are rejected at construction time, and parsed URLs with an empty host are rejected. TestConnection-style checks and previously-stored destinations are unaffected once the daemon restarts. The same constructor now also TrimSpaces access_key and secret_key to defend against the related copy-paste failure where stray whitespace from the B2 console produced a 403 SignatureDoesNotMatch with no obvious cause.
    • WebDAV chunked uploads to Nextcloud (and other Sabre/DAV servers) no longer fail with WriteStreamWithLength …/000000.part: 400. The WebDAV adapter wrote each chunk of a logical-file upload as <index>.part inside the .chunks sidecar directory. Nextcloud's default forbidden_filename_extensions / blacklisted_files_regex reserves .part and .filepart for its own in-progress-upload mechanism and rejects external PUTs to those names with HTTP 400 Bad Request. Single-PUT uploads (small backups, < 50 MiB) were unaffected, so TestConnection and small jobs passed while every chunked container backup failed on the first chunk. Chunk files are now written with a .dat suffix, which is not on any known WebDAV server blacklist. The fix is forward-only safe: every chunk's absolute path is recorded in the manifest, so historical restore points continue to read correctly from their original .part chunks. writeChunked's cleanup path also now removes the (empty) .chunks collection when a chunked upload aborts on the first chunk, so failures leave nothing behind on the remote.
    • Dedup ratio and logical-bytes stats are correct for multi-item dedup destinations. The Storage card's dedup ratio showed 0× / 0 B → N (and the diagnostics bundle reported zero logical bytes) for any destination fed by a multi-item job – e.g. a containers dedup backup. DedupAggregates summed restore_points.size_bytes only WHERE manifest_id IS NOT NULL, but that column is set only for single-item jobs; multi-item jobs leave it NULL and store per-item IDs in metadata.item_manifests, so their logical bytes were excluded entirely. The query now sums every restore point for the destination's jobs (the destination is already known to be dedup-enabled and dedup mode is immutable per destination), so the ratio reflects real savings.
    • GC no longer deletes live data from large container/plugin dedup backups. A container's dedup manifest references its volume file data only indirectly: each __vol__<dest> entry points at a sub-manifest, which lists the actual data chunks. GC's reachability set (collectLiveManifestIDs, used by both the daemon's POST /storage/{id}/gc and the vault dedup gc CLI) collected only the top-level manifest IDs, and GC marks just the direct chunks of each live manifest – so the volume data chunks were never marked. Any pack containing only such chunks (i.e. every data-only pack of a backup larger than one 24 MiB pack) was swept, silently corrupting the backup; the next restore would fail with missing chunks. The live set is now expanded through a new engine.WalkManifestClosure that recurses into volume sub-manifests, so every reachable chunk is marked. Folder/plugin single-level backups were unaffected; small single-pack container backups happened to survive because their data shared a pack with a manifest chunk. Confirmed with a multi-pack regression test.
    • Deep and quick verify now work on multi-item dedup restore points and actually re-hash container volume data. Verify keyed off restore_points.manifest_id, which is only set for single-item dedup jobs; a multi-item job (e.g. a containers backup) stores per-item IDs under metadata.item_manifests and leaves manifest_id empty, so verify fell through to the classic per-file path and failed with "no recorded file checksums in restore point metadata". Verify now detects a dedup restore point from either source, walks every item's manifest closure (including the nested volume sub-manifests), and in deep mode re-reads + re-hashes every leaf data chunk – previously even a single-item container deep verify only checked the top-level manifest's pointer chunks, not the file data. Quick mode stats the unique packs across the full closure.
    • Dedup (chunked) backups now honour container/folder path exclusions, matching the classic tar pipeline. ContainerHandler.BackupChunked ignored the job's exclude_paths entirely: it never applied shouldExcludeMount (so a whole-mount exclusion like /rootfs was skipped) and never mapped per-volume globs into the chunk walk. A container that bind-mounts the host root (Glances, Telegraf, Netdata: / → /rootfs) therefore had its entire host filesystem content-chunked into the dedup repo despite a /rootfs exclusion – slow runs, a bloated repo, and unrelated host files (boot/, lib64/, mnt/cache/appdata/…) appearing in the restore-point file list. The chunked path now reads exclude_paths, skips excluded mounts wholesale (recorded as skipped volumes), and passes volume-relative patterns through to the walk. FolderHandler.BackupChunked (used directly for folder/plugin dedup jobs and for each container volume) now applies the same shouldExcludePath filter the tar path uses – a matching directory is pruned (SkipDir) and never traversed. Classic tar backups were already correct; only the dedup path was affected.
    • Running dedup backups no longer display "-1%" in the Dashboard progress list. The daemon emits -1 as an "indeterminate progress" sentinel during the streaming chunk walk (total size isn't known up front). The per-item progress bar rendered this literally as a "-1%" label and a negative-width bar. Negative percent is now treated as indeterminate: the bar pulses at full width and the numeric label shows ··· until a real percentage arrives.
    • "Include in DB backup" toggle on the Storage page now persists. Two coordinated bugs hid behind the toast. (1) UpdateStorageDestination did not include backup_database_enabled in its UPDATE clause, so the DB silently dropped the field. (2) The storage PUT handler decodes into a partial-patch struct that omitted the field, so the request body's value was thrown away before even reaching the DB. Both were corrected.
    • retry_max_override and retry_delays_override (job edit) + retry_of_run_id / retry_next_at (job runs) now serialise as native JSON null / number / string instead of {"Valid":false,"Int64":0} wrapper objects. The override-retry input previously showed "[object Object]" with an "Invalid JSON" error because the form bound the wrapper struct directly. Backend struct fields are now pointer types (*int64, *string, *time.Time) so database/sql round-trips nullables transparently and the JSON encoder emits clean values.
    • Activity log details render duration as 1 min, 2.0 s, 7 min 10 s etc. instead of raw 60002ms / 430s. A new formatDuration helper in Logs.svelte handles both duration_ms and duration_seconds detail keys.

    • Retry policy delays are no longer a JSON textbox. Both Settings → Retry Policy and Job edit → Override retry policy now use a friendly editor: preset dropdown (Default 15 m / 1 h / 4 h, Aggressive 1 m / 5 m / 15 m, Patient 1 h / 6 h / 24 h, Custom) plus per-row [number] [unit ▾] rows with + Add / × Remove. The override section adds a "Use global default" checkbox that hides the editor and emits an empty value (= NULL on save).

    • S3-compatible uploads (MinIO, MEGA, IDrive E2, Backblaze B2 via S3) no longer fail with 403 SignatureDoesNotMatch when the job name contains spaces or other URL-reserved characters. The aws-sdk-go-v2 + custom endpoint resolver + path-style combo has a signing-vs-sending URL-encoding asymmetry that breaks every PutObject and DeleteObject for keys containing reserved characters. TestConnection (HeadBucket) keeps passing because it has no path beyond the bucket – the "test passes, every upload fails" fingerprint. The S3 adapter now sanitizes each key path segment to the RFC 3986 unreserved set before sending to the SDK. Both Write and Read use the same translation, so existing backups continue to restore and new backups produce sanitized keys that all gateways accept (closes follow-ups on #88).

    • S3 PutObject no longer attaches a CRC32 SigV4 trailer that breaks S3-compatible gateways. The 2026.05.02 fix set the global RequestChecksumCalculation=WhenRequired but the upload-layer client hard-codes its own CRC32 default, so the trailer was attached anyway. The S3 adapter now uses the stable feature/s3/manager.Uploader, which honours the global setting correctly. Multipart PartSize binding (640 GB → 10 TB per-object ceiling for large streams) is preserved.
    • Container backups for containers that bind-mount the host root (Glances, Telegraf, Netdata, cAdvisor, node-exporter with / → /rootfs) no longer recursively walk the host filesystem before the volume is skipped. The 2026.05.01 fix moved the exclusion check above the per-volume backup branch, but the auto-compression-downgrade pre-scan still ran on the bind-mount source first – a full filepath.Walk of the host root. A Test Containers job that took 37 s before regressed to 14 minutes. The exclusion check now genuinely runs first; the compression pre-scan only touches volumes that will actually be archived. Same job is back to 38 s.
    • PUT /api/v1/storage/{id} no longer destroys the destination when the caller sends a partial body. The handler was decoding into a fresh struct and writing the whole row, so a request like {"config":"..."} blanked name, type, and dedup_enabled and orphaned every job pointing at the destination. It now loads the existing row, merges only the fields explicitly provided, and rejects attempts to change immutable fields (type, dedup_enabled) with HTTP 400.
    • POST /api/v1/storage no longer leaks the plaintext password / S3 secret key in its 201 response. Get() redacted the config blob but Create() echoed the request body verbatim – credentials were visible in browser devtools' Network tab during Add Storage. Both Create() and Update() now re-fetch the persisted row and apply the same redaction.
    • POST /api/v1/storage now validates the type and config before persisting. Previously accepted arbitrary types ({"type":"bogus"} was 201-ed) and empty configs that could never construct a working adapter. Both Create() and Update() now build the adapter up-front and return HTTP 400 on construction failure with the underlying error.
    • POST /api/v1/jobs and PUT /api/v1/jobs/{id} now include the persisted items in their response so callers can chain on the server-assigned item IDs. Job fields stay at the top level for backwards compatibility (result.id still works).
    • GET /api/v1/storage/{id}/jobs returns the list of dependent jobs, not just a scalar count. Response now includes a jobs array of {id, name} so the UI can show which jobs would be orphaned by a delete. job_count is preserved.
    • GET /api/v1/storage/{id}/dedup-stats no longer returns 500 on a freshly-created dedup destination that hasn't run a backup yet. The Storage card now renders "0 chunks · 0 packs" instead of a broken-card state until real stats start flowing.
    • GET /api/v1/jobs/{id}/restore-points/{rpid}/contents?item=… now works on dedup restore points instead of returning 500. The handler previously expected a per-item tar archive directory; dedup destinations don't have one. It now synthesizes the file list from the dedup manifest's per-file metadata so the restore-wizard file picker works for both classic and dedup restore points.
    • Recovery page no longer flags items as Unprotected when their owning job is disabled. The recovery API correctly reports has_restore_point: true regardless of the parent job's enabled flag, but the Svelte page derived its own protected set from enabled jobs only, so disabling a schedule (a common manual-only workflow) made items appear unprotected even though their backups were intact. The page now derives protection from has_restore_point directly, matching the API. The Dashboard's matching logic was updated the same way.
    • Recovery plan step status now considers every item, not just the first. The handler previously checked only items[0] to badge a step "ready" or "warning"; a step with one missing restore point but several intact ones was shown as ready. It now downgrades to "warning" if any item is missing.
    • Restore wizard file picker no longer hangs on "Loading…" after expanding "Restore specific files". The per-item state was held in a SvelteMap whose value objects were mutated directly after an await boundary – SvelteMap doesn't propagate mutations across awaits, so the UI never received the loading: false flip. The picker now writes a fresh object reference on every transition.
    • Folder/Plugin Items wizard step no longer falsely flags every custom folder as "Not found". The stale-detection check compared selected items against /api/v1/folders, which only returns engine-discoverable presets like the Flash Drive – so any user-added custom folder appeared "not found" even when the path was perfectly valid. A new GET /api/v1/path-exists?path=… endpoint does a safepath-validated os.Stat; the picker now async-checks every custom folder's path on mount and only flags it when the stat actually fails. The empty-state message was also rewritten to point users at the "Add Custom Folder" workflow instead of looking like an error.
    • Dedup stats endpoint now reports correct totals across daemon restarts and from any goroutine. Stats() previously returned in-memory counters that only the writing process saw, so the Storage card showed zeros after a restart. It now reads totals from SQL aggregates and derives logical bytes from restore_points.size_bytes summed over the destination's live dedup restore points.
    • GET /api/v1/jobs/{id}/history and /restore-points return [] (not JSON null) for jobs with no rows. Front-end code that called .length or .map() on the response was throwing.
    • GET /api/v1/activity?limit=N clamps limit to ≤ 1000 to prevent an authenticated caller (or misconfigured monitor) from OOM-ing the daemon by requesting a huge limit.
    • WebSocket origin patterns now cover the entire RFC 1918 172.16.0.0/12 range (172.16.x.x through 172.31.x.x). Previously only 172.16.*.* was listed, so users on 172.17.0.0/16 (Docker's default network) through 172.31.x.x never received progress updates.
    • Password inputs across Settings, Storage, Restore wizard, and Replication forms now declare appropriate autocomplete attributes so browsers stop offering inappropriate suggestions and the verbose DOM warning on focus goes away.
    • Failed backup jobs no longer leave orphaned partial uploads at the destination. When the upload retry loop exhausted (or hit a verify mismatch or context cancellation), the runner returned without cleaning up the per-item files it had already written, wasting remote quota and confusing the next run. It now best-effort deletes every partial file before surfacing the error.
    • WebDAV chunk uploads use exponential backoff with HTTP-status-aware retry classification. Chunk PUTs retry on 423 Locked, 409 Conflict, 429 Too Many Requests, any 5xx, stall-watchdog timeouts, and transport errors (100ms → 300ms → 1s → 3s → 8s, 6 attempts). Permanent 4xx failures (401, 403, 404, 413, …) fail fast on the first attempt instead of consuming the full retry budget.
    • WebDAV uploads no longer buffer non-seekable backup streams into memory or leave encryption goroutines alive after stalled retries. Bounded objects use WriteStreamWithLength so the fallback that copies unknown-length streams into RAM is avoided (closes #96).
    • Large WebDAV backups are split into manifest-backed chunks instead of one monolithic PUT. Files larger than the configured WebDAV chunk size upload as independent fixed-size objects with per-chunk SHA-256 hashes and a manifest written last. Restore, verify, list, stat, and delete are manifest-aware while older single-file WebDAV backups remain readable (closes #97).
    • Importing dedup backups from another Vault instance now produces restorable restore points. manifest.json written to storage didn't include per-item dedup manifest IDs, and the import path didn't read them either – so re-discovered dedup backups appeared in the UI but the restore would fail because the chunks were unreachable. writeManifest now embeds item_manifests for dedup runs, and ImportBackups reads the field back, persisting per-item IDs in the restore-point metadata and promoting the ID onto the row directly for single-item dedup jobs. Non-dedup imports are unchanged. Manifests written before this change still import as classic file-based restore points (no regression).
    • Dead code cleanup: Server.Start, SettingsHandler.RestorationInfo, Client.GetJob, Syncer.SetHub, parseDomainDisks/domainDiskPaths, and decompressReader/fileCompressionExt removed. Each was either superseded by a context-aware variant, replaced by a content-based equivalent, or had no callers in the live tree.
    • Daemon now flushes the DB snapshot to USB flash after every config mutation, not just on startup/shutdown. Server.SetConfigChangeHook stored the hook on the Server struct but never forwarded it to the per-handler onConfigChange fields, so every notifyConfigChange() call across the four CRUD handlers was a no-op. The Server now stashes references to all four handlers and propagates the hook. StorageHandler and ReplicationHandler gained the missing hook plumbing too – every Create/Update/Delete now triggers the flush.

    Security¶

    • Folder dedup restore now validates every manifest path against the destination root before writing. FolderHandler.RestoreChunked joined every manifest entry to destPath with filepath.Join, which does not prevent .. segments from escaping the target directory. A tampered manifest at the storage destination could therefore have caused the restore to write files outside the chosen recovery folder (CWE-22 / CodeQL go/path-injection). Every entry now goes through safepath.JoinUnderBase, which rejects any path that wouldn't stay inside destPath. Closes CodeQL alerts #32–#35.
    • Pack writer now bounds its pre-allocation size. The pack-flush path allocated a buffer sized by bufLen + footerLen + 4 without an explicit cap. In practice these values are bounded by PackTargetSize (24 MiB) plus one chunk's slop, but CodeQL go/allocation-size-overflow couldn't see that. An explicit ceiling (PackTargetSize * 4) is now enforced with a clear error if exceeded. Closes CodeQL alert #37.
    • Discord-webhook log redaction now anchors on the https:// scheme prefix so it only matches genuine webhook URLs, not arbitrary log text that happens to mention the substring discord.com/api/webhooks/…. Behavioural impact is nil for real logs (the existing test still passes) but the regex now satisfies CodeQL go/regex/missing-regexp-anchor. Closes CodeQL alert #36.

    [2026.05.02] - 2026-05-15¶

    Fixed¶

    • S3 / Backblaze B2 uploads of multi-GB objects no longer abort with context deadline exceeded mid-multipart (closes #95). The S3 adapter previously routed every operation – including large multipart uploads via transfermanager.Uploader – through a single hardcoded 5-minute context (ctxOp). A real Immich-style folder backup to Backblaze B2 exceeded that ceiling well before the upload (and its in-flight AbortMultipartUpload cleanup) could complete, producing a cascading context-cancellation failure. Upload operations are now scoped to a separate, configurable deadline (uploadTimeout, default 240 minutes / 4 hours) while metadata operations (Read / List / Stat / Delete / TestConnection) continue to use the existing 5-minute budget unchanged. A new optional upload_timeout_minutes field on the S3 storage config – surfaced in the Storage form as "Upload timeout (minutes)" under the existing advanced options – lets users tune the ceiling for very large files over slow links (set 0 to accept the 4-hour default; negative values are rejected at construction time).
    • Restored Docker containers now keep their port mappings – Unraid's "Container Port" and "LAN IP:Port" columns no longer go blank after a restore. Container backups capture Config.ExposedPorts and HostConfig.PortBindings from docker inspect, but the restore path declared a local portBindings map and immediately discarded it (_ = portBindings // avoid unused variable) without ever populating it from the inspect data or assigning it to the new container.HostConfig. Restored containers were therefore created with zero exposed ports and zero host-port bindings, which is exactly what Unraid's Docker page renders as a blank port column. The user could "fix" the row by clicking Edit → Done because Unraid then rebuilds the container from the on-disk template XML, masking the bug. The restore engine now converts both maps into the typed network.PortSet and network.PortMap the Docker API requires (parsing keys with network.ParsePort and netip.ParseAddr, skipping malformed entries with a log line), and assigns them to containerConfig.ExposedPorts and hostConfig.PortBindings respectively. Empty/invalid HostIP values are left as the zero netip.Addr so Docker treats them as "bind on all interfaces", matching its own default. Restored containers now show their port mappings immediately, with no Edit→Done dance required.
    • Restored Docker containers now show their correct update status in the Unraid Docker Manager UI instead of "not available". Unraid computes a container's "up-to-date" / "update available" badge by reading RepoDigests[0] from each image's metadata, but docker load (used during restore) does not populate RepoDigests – only docker pull does. As a result, restored containers showed "not available" and the "Check for Updates" button could not resolve a local digest, leaving the badge stuck. The container engine now captures each image's RepoDigests at backup time into a small image_meta.json companion file (alongside image.tar*), and the restore path uses that to re-seed /var/lib/docker/unraid-update-status.json with the recorded local digest after ImageLoad. The Unraid UI then resolves "up-to-date" or "update available" immediately, and "Check for Updates" works against the restored container. Verified end-to-end on Unraid against the "Test Containers" job: Grafana, Influxdb, and telegraf all flipped from "not available" to "up-to-date" after a fresh backup→restore cycle.
    • Restore now also performs a docker pull after ImageLoad to authoritatively populate RepoDigests for the restored image. This handles the chicken-and-egg case where the source container's image itself had no RepoDigests at backup time (e.g. the image was previously restored from tar without ever being pulled, or the user is upgrading from a Vault version older than the image_meta.json capture), in which case the backup's image_meta.json recorded repo_digests: null and the prior unraid-update-status.json seeder had nothing to write. The pull is non-destructive – when layers already exist locally (the common case immediately after ImageLoad) Docker only fetches the manifest, which is exactly the metadata required. The freshly-pulled digest is then written directly into unraid-update-status.json, so the badge flips to "up-to-date" without depending on the backup's recorded metadata. If the daemon is offline or the registry is unreachable, the call fails silently and the path falls back to image_meta.json-based seeding. Verified end-to-end on Unraid: nicolargo/glances:latest (which had empty RepoDigests on the host from a prior tar-only restore) flipped from "not available" to "up-to-date" after restore-with-pull.
    • Container Path Exclusions now skip directory bind mounts at the volume level (closes #70). The earlier fix (2026.05.01) only applied exclusion patterns to single-file bind mounts. Directory mounts – most notably the recursive / → /rootfs mount used by Telegraf, Netdata, cAdvisor, Glances, and Prometheus node-exporter – still entered the recursive walk and only filtered special-file inodes, so the engine eventually started archiving the host filesystem (including the array into itself) and the job hung indefinitely. Exclusion matching now runs once, up front, against every bind mount's container-side destination regardless of whether the mount is a file or a directory, mirroring the single-file behaviour the user reported as working. Verified end-to-end on Unraid with a real "Test Containers" job (Influxdb + Grafana + Glances + Telegraf, both Glances and Telegraf bind-mounting / → /rootfs): job completed in 37 s (4/4 items, 1.9 GB) with engine: skipping volume / … matches exclusion pattern in the daemon log, replacing a previous 13 m 37 s hang that failed at 2/4 items.
    • Compression setting now controls the actual on-disk archive format. Previously the engine always emitted gzip-wrapped tar archives while the runner additionally wrapped the upload stream with whatever compression the user selected, so jobs configured for zstd shipped double-compressed volume_*.tar.gz.zst files and jobs configured for None still produced .tar.gz. The engine (internal/engine/container.go, folder.go, plugin.go) is now the single source of truth for archive compression and emits .tar, .tar.gz, or .tar.zst per BackupItem.Compression, while the runner's upload path no longer wraps the stream a second time. Restore auto-detects the format via magic bytes (0x1f 0x8b for gzip, 0x28 0xb5 0x2f 0xfd for zstd, plain otherwise) and the engine looks up archives by trying base, base+".gz", and base+".zst" in turn, so existing .tar.gz backups (and legacy double-wrapped .tar.gz.zst files via the runner-side decompressStoredReader) continue to restore correctly. Verified end-to-end on Unraid against the "Test Containers" job: none → .tar, gzip → .tar.gz, zstd → .tar.zst.
    • Restore wizard "Choose Version" step now shows the absolute date alongside the relative offset inline (closes #81 follow-up from @SebboGit). The previous fix relied on a native title tooltip to surface the relative time on hover, but native browser tooltips were unreliable on the parent button row (Firefox in particular suppresses them when the <span> lives inside a role="button"/cursor: pointer ancestor). Both forms are now rendered together as 12 May 2026, 02:09 am · 7h ago, giving an unambiguous absolute timestamp with the relative offset always visible – no hover required, works on touch.
    • Logs page no longer collapses expanded "Details" rows every 5 s during auto-refresh. loadLogs() previously called expandedIds.clear() on every poll cycle and re-added only error rows, so any non-error row a user had manually expanded was wiped on the next refresh. The expanded set is now preserved across reloads, entries that have aged out of the visible window are pruned, and the auto-expand-error behaviour now tracks a separate "already auto-expanded" set so collapsing an auto-expanded error keeps it collapsed.
    • Failed backup jobs no longer leave orphaned partial uploads at the storage destination. When uploadStagedFiles exhausted its 4-attempt retry loop (or hit a verify mismatch or ctx cancellation), it returned an error without cleaning up the per-item files it had already successfully uploaded, or the partially-written bytes from the failing item. This wasted remote-storage quota (especially painful on quota-bounded providers like Hetzner Storage Box) and made the destination directory look "half done" to the next run. The runner now performs best-effort adapter.Delete() on every known partial file before returning the error. Cleanup failures are logged but never mask the original upload error.

    • WebDAV uploads of multi-GB files no longer fail with context deadline exceeded ... Client.Timeout exceeded while awaiting headers (closes #83 follow-up from @SebboGit). The WebDAV adapter previously called gowebdav.Client.SetTimeout(60*time.Second), which maps to http.Client.Timeout – a single deadline that covers the entire request lifetime, including the upload body. A 20-container backup to Hetzner Storage Box repeatedly failed during the upload-retry loop (4× exponential-backoff attempts per item, all timing out at the same 60 s mark), eventually crashing the daemon. The fixed 60 s deadline is replaced with phase-specific http.Transport timeouts that do not bound body-transfer duration:

    • TCP dial 30 s, TCP keepalive 30 s

    • TLS handshake 30 s
    • Expect-Continue 5 s
    • Response headers 5 min (applies AFTER the body is fully sent)
    • Idle keep-alive 90 s
    • http.Client.Timeout left at 0 (unlimited) by default

    In addition, every upload reader is now wrapped in a stall watchdog: it records the timestamp of every successful Read() and aborts the PUT with webdav: upload stalled when no bytes flow for the configured window (default 300 s / 5 min).     Fixed¶

    • VM checkpoint creation now succeeds for cold (shut-off) backups. Previously the engine called DomainCheckpointCreateXML against the persistent domain handle after restoreDomainState() had already destroyed the transient paused session – libvirt rejected the call with "Operation not supported: cannot create checkpoint for inactive domain", so every cold incremental/differential ran without ever recording a parent checkpoint and silently fell back to producing a full-size qcow2. Checkpoints are now created against the live (paused) backupDom while the transient backup session is still active, and only after the bitmap is persisted to qcow2 does the runner tear the session down. End-to-end verified against a cold Fedora VM: full = 2.3 GB, incremental and differential = 192 KB on a no-change cycle.
    • Engine no longer reports "incremental" / "differential" when no parent checkpoint is recorded. When the runner had no checkpoint metadata to pass (first run after a chain reset), the engine still produced a full-size backup but labelled the result vm_backup_type: incremental, which corrupted the chain bookkeeping. The fall-back logic now also covers the empty-parent case and downgrades actualType to "full" with a clear log entry before writing vm_meta.json and result.Meta.
    • VM incremental backups now actually capture only changed blocks. Previously every "incremental" or "differential" run silently produced a full copy of each qcow2 disk: the engine emitted a regular libvirt push-mode backup XML with no <incremental> element, and the only "incremental" behaviour was a file-mtime gate that either (a) re-copied the whole disk anyway when the VM was running (mtime always advanced) or (b) skipped the disk entirely when the VM was cold (mtime unchanged after the previous backup) – silently losing data. The engine now creates a libvirt checkpoint (persistent dirty bitmap stored in qcow2) after each successful backup and references it via <incremental>parent_checkpoint</incremental> on subsequent runs, so libvirt streams only the dirty blocks since the parent checkpoint. Restore points record the checkpoint name in vm_checkpoints metadata; missing-parent or non-qcow2 disks fall back to a full backup with a clear log entry. Retention cleanup deletes orphaned libvirt checkpoints. (closes the broken VM Incremental / Differential modes)
    • Backups failing with No space left on device when staging to /mnt/addons (1 MB tmpfs). The pool-discovery cascade in internal/unraid/pools.go selected any directory that exists under /mnt/, which on modern Unraid includes the /mnt/addons tmpfs mount.
